# Terraform Service Documentation

## Overview

This module (`app/services/terraform.py`) acts as the secure bridge between the Python application and the **Terraform CLI**. It handles the generation of Infrastructure as Code (IaC) configurations, manages temporary job directories, and executes the Terraform lifecycle (init, workspace management, apply, destroy).

It generates HCL (HashiCorp Configuration Language) programmatically and implements strict security measures to ensure sensitive credentials are passed via environment variables rather than configuration files.

## Security & Credential Management

### Environment Variable Injection

To prevent sensitive credentials from being written to disk (in `terraform.tfvars` or `main.tf`), this service injects secrets directly into the Terraform process environment.

*   **Backend Connection String:** The `DATABASE_URL` is passed to Terraform via the `TF_BACKEND_CONN_STR` environment variable.
*   **Variable Exclusion:** The `backend_conn_str` key is explicitly filtered out of the `variables` dictionary before generating `terraform.tfvars` files.

### Log Sanitization

All logs generated by this service are sanitized to prevent leaking credentials.

*   **URL Parsing:** The `_mask_connection_string` helper uses `urllib.parse` to intelligently mask passwords in connection strings (e.g., `postgresql://user:pass@host` becomes `postgresql://user:***@host`).
*   **Sensitive Keys:** The `SENSITIVE_KEYS` list (40+ patterns including `password`, `secret`, `token`, `api_key`, `private_key`, `backend_conn_str`) drives automatic log redaction via `sanitize_for_logging`.

### Secure Temp Directories

*   `_create_secure_temp_dir()` creates directories with `0o700` permissions (owner-only access)
*   `_secure_cleanup()` recursively chmods files to owner-only before deletion
*   Configurable via `TERRAFORM_TEMP_DIR` environment variable

## Helper Functions

### 1. Mask Connection String

**Signature:** `def _mask_connection_string(conn_str: str) -> str`

**Description:**
Uses `urllib.parse` to robustly mask passwords in connection strings. It handles standard URL formats and preserves port numbers and paths.

**Usage:**
```python
# Input: postgresql://admin:secret123@db.example.com:5432/mydb
# Output: postgresql://admin:***@db.example.com:5432/mydb
```

### 2. Sanitize for Logging

**Signature:** `def sanitize_for_logging(data: Dict) -> Dict`

**Description:**
Masks sensitive values in a dictionary intended for log output. It checks keys against a `SENSITIVE_KEYS` list and uses regex to mask credentials embedded in URL strings.

### 3. Get Safe Variable Name

**Signature:** `def get_safe_variable_name(key: str) -> str`

**Description:**
Returns a display-safe version of a variable name, appending `(redacted)` if the key implies sensitive data.

## Core Functions

### 1. Get Terraform Context (VMs)

**Signature:** 
```python
def get_terraform_context(
    vm_request, 
    vm_id: int, 
    db: Session = None
) -> Tuple[str, Dict]
```

**Description:**
Determines which Terraform template to use and generates the dictionary of variables required for VM provisioning.

**Logic:**
1.  Extracts the provider from the request object.
2.  **Network Lookup:** If `network_id` is provided, queries the `TenantNetwork` table to retrieve network configuration.
3.  **Variable Construction:** Builds the dictionary.
    *   **Security Note:** `backend_conn_str` is **NOT** included in the returned dictionary; it is handled via environment variables in the execution function.
4.  **Provider Specifics:**
    *   **Proxmox:** Uses `proxmox_clone.tf.j2` template with template ID, VLAN, credentials from settings.

**Generated Variables (Proxmox):**

| Variable | Type | Description |
|----------|------|-------------|
| `vm_id` | int | Unique VM identifier |
| `vm_name` | string | Name of the VM |
| `template_id` | int | Proxmox template ID |
| `cpu` | int | CPU cores |
| `ram` | int | Memory in MB |
| `disk_size` | int | Disk size in GB |
| `vlan_tag` | int | VLAN tag for network |
| `node` | string | Proxmox node name |
| `storage` | string | Storage pool |

**Returns:**
- `template_name`: Filename of the Jinja2 template (e.g., `"proxmox_clone.tf.j2"`)
- `variables`: Dictionary of key-value pairs for template rendering

### 4. Run Terraform Job (Provisioning)

**Signature:** 
```python
def run_terraform_job(
    identifier: int, 
    name: str, 
    tf_code: str, 
    variables: Dict, 
    workspace_prefix: str = "vm"
) -> Dict
```

**Description:**
Executes the full Terraform workflow to provision infrastructure. Handles workspace creation, secure variable passing, and real-time logging.

**Workflow:**

```
1. Secure Temp Directory Creation
   └── Creates 0o700 permission temp dir

2. Configuration Files
   ├── main.tf          (rendered HCL code)
   └── terraform.tfvars (formatted variables, EXCLUDING backend_conn_str)

3. Environment Preparation
   ├── TF_BACKEND_CONN_STR = settings.DATABASE_URL
   ├── TF_IN_AUTOMATION = true
   └── TF_CLI_ARGS = -no-color

4. Terraform Init (timeout: 300s)
   └── Initializes providers and backend

5. Workspace Management (timeout: 30s)
   ├── Attempt: terraform workspace new {prefix}_{identifier}
   │   └── Ignore error if already exists
   └── Select: terraform workspace select {prefix}_{identifier}

6. Terraform Apply (timeout: 3600s)
   └── terraform apply -auto-approve -var-file=terraform.tfvars
       (Streams stdout to logger and WebSocket in real-time)

7. Output Extraction (timeout: 30s)
   ├── vm_internal_ip
   └── vm_external_port

8. Secure Cleanup
   └── Recursive chmod + rmtree (state preserved in backend)
```

**Returns:**
```json
{
  "status": "success",
  "outputs": {
    "ip": "172.20.0.5",
    "port": "8005"
  }
}
```

### 5. Destroy Terraform Job

**Signature:** 
```python
def destroy_terraform_job(
    identifier: int, 
    name: str, 
    tf_code: str, 
    variables: Dict, 
    workspace_prefix: str = "vm"
) -> Dict
```

**Description:**
Executes the cleanup workflow to permanently remove infrastructure resources. It targets the specific workspace identified by the `identifier` and `prefix`.

**Workflow:**

```
1. Secure Temp Directory Creation
2. Configuration Files (Regenerated from DB state)
3. Environment Preparation (TF_BACKEND_CONN_STR)
4. Terraform Init (timeout: 300s)
5. Workspace Selection (Must exist: terraform workspace select)
6. Terraform Destroy (timeout: 3600s, real-time logging)
7. Secure Cleanup
```

**Returns:**
```json
{
  "status": "destroyed"
}
```

## Workspace Management

### Overview

The service uses Terraform Workspaces to isolate state files for different resources. Each resource gets its own workspace named `{prefix}_{identifier}`.

### Lifecycle Logic

**Provisioning (`run_terraform_job`):**
1.  **Attempt Create:** Runs `terraform workspace new`.
2.  **Handle Exists:** If the command fails (workspace already exists), the error is caught and logged.
3.  **Select:** Runs `terraform workspace select` to ensure the correct workspace is active.

**Destruction (`destroy_terraform_job`):**
1.  **Select:** Directly runs `terraform workspace select`. It assumes the workspace exists; if not, the command fails (indicating the resource is already gone or state is missing).

## Error Handling & Logging

### Exception Handling Strategy

| Scenario | Behavior |
|----------|----------|
| Terraform `init` fails | Raise `TerraformExecutionError`, secure cleanup temp directory |
| Terraform `apply` fails | Raise `TerraformExecutionError`, secure cleanup temp directory |
| Terraform `destroy` fails | Raise `TerraformExecutionError`, secure cleanup temp directory |

**Note on Cleanup:** The service cleans up the temporary job directory in all cases (success or failure) using `_secure_cleanup()` (recursive chmod before rmtree). State is preserved in the remote backend (PostgreSQL), so the local directory is disposable.

### Logging Strategy

| Level | Usage |
|-------|-------|
| `INFO` | Job start/end, workspace operations, real-time TF output (`[TF INIT]`, `[TF APPLY]`) |
| `DEBUG` | Template rendering details, masked backend connection string |
| `WARNING` | Missing outputs, failure to render init scripts |
| `ERROR` | Command failures, job exceptions |

### Log Prefixes

To distinguish between different stages in the logs:

```
[TF INIT] Initializing the backend...
[TF APPLY] docker_container.web: Creating...
[TF DESTROY] docker_container.web: Destroying...
```

All logged variable dictionaries are passed through `sanitize_for_logging` to ensure secrets are redacted.
